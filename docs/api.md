# HTTP API

Feedway exposes one authenticated publishing endpoint, a public home page, an
aggregate JSON Feed and filtered JSON Feeds, public entry pages and optional
JSON attachments, and two operational probes. Paths are relative to the HTTP
origin where the container is published.

## Feed identifiers

An entry may have an optional feed identifier. Identifiers are ASCII slugs of
1–64 bytes: lower-case letters and digits, separated by single hyphens. They
cannot start or end with a hyphen or contain consecutive hyphens. Feedway does
not trim whitespace or fold case. For example, `daily-briefing` is valid;
`Daily-Briefing`, `daily--briefing`, and ` daily-briefing ` are invalid.

There is no feed registry, display-name metadata, or feed-management API. A
producer can use any valid identifier without creating it first. Entries with
no identifier belong only to the aggregate feed.

## Authentication

Only `POST /api/v1/entries` requires authentication. Send the deployment's
`API_TOKEN` as a Bearer token:

```http
Authorization: Bearer <API_TOKEN>
```

Missing or invalid credentials return `401 Unauthorized` with the common error
shape:

```json
{"error":"unauthorized"}
```

The response also includes:

```http
WWW-Authenticate: Bearer
```

The home page, feeds, individual entry pages, JSON attachments, and probes are public.
Put TLS and any additional access control at a reverse proxy when the service is exposed beyond
a trusted network.

## Browse available feeds

### `GET /`

Returns a minimal HTML home page titled `Feedway`. It lists each distinct,
non-null feed identifier currently present on retained entries, sorted by
identifier. Each row has a decorative RSS icon and an origin-root-relative
link to `/feeds/{feed}/feed.json`; the linked representation is JSON Feed,
not RSS XML. Labels replace hyphens with spaces and capitalize each word,
for example `daily-briefing` becomes `Daily Briefing`. Labels are derived
from identifiers, not stored metadata.

The page lists all available identifiers regardless of `FEED_RESPONSE_MAX_ENTRIES`
and the 4 MiB JSON Feed response limit. Entries without an identifier do not
create a list item. The page shows `No feeds yet.` when no named feeds exist,
including a database containing only unassigned entries. After retention
deletes the last entry assigned to an identifier, that feed disappears from
the list. Its filtered feed URL continues to return an empty JSON Feed.

The page contains inline CSS and SVG icons, without JavaScript or external
assets. Successful responses use:

```http
Content-Type: text/html; charset=utf-8
Content-Length: <response bytes>
X-Content-Type-Options: nosniff
```

A database or rendering failure returns `500 Internal Server Error` with a
generic plain-text body; internal details are logged. The page does not
provide ETag or conditional requests.

### `HEAD /`

Returns the same status and headers as `GET /` without a response body.
Only the exact root path serves the home page; unknown paths still return `404`.

## Publish an entry

### `POST /api/v1/entries`

Content type must be `application/json`. The request body is limited to 1 MiB,
unknown fields are rejected, and the JSON object contains:

| Field | Required | Limit | Description |
| --- | --- | --- | --- |
| `content_html` | yes | 256 KiB before and after sanitization | HTML body of the entry |
| `title` | no | 1,000 Unicode characters | Entry title |
| `feed` | no | 1–64 bytes when non-null | Feed identifier; omitted or `null` means unassigned |
| `data_json` | no | 256 KiB | Native JSON value accompanying the entry |

Example:

```bash
curl --fail-with-body \
  --request POST \
  --header "Authorization: Bearer $API_TOKEN" \
  --header 'Content-Type: application/json' \
  --data '{
    "title": "Morning briefing",
    "content_html": "<h2>Today</h2><p>Three systems reported healthy.</p>",
    "feed": "daily-briefing"
  }' \
  http://localhost:8080/api/v1/entries
```

Feedway normalizes line endings and surrounding whitespace, sanitizes the HTML,
and computes a `sha256-v1` content hash from the final title and sanitized HTML.
For each feed, the pair `(feed, content_hash)` identifies a publication for
retry deduplication. `data_json` does not affect this key. New entries receive
an opaque, stable UUIDv7 ID generated by PostgreSQL 18; IDs already stored in
older databases keep their existing `sha256-v1:<hex>` values.

Publishing the same final title and HTML to the same feed again is safe. The
first request returns:

```http
201 Created
```

```json
{"result":"created","id":"0190abcd-1234-7abc-8def-0123456789ab"}
```

An identical retry to the same feed returns `200 OK` with
`"result":"deduplicated"` and the same ID. Publishing the same content to a
different feed creates a separate entry with its own ID and independent
attachment state.
Omitting `feed` or sending `null` publishes the entry only in the aggregate
feed; it does not assign it to a named feed. A producer that needs every run to
appear separately in one feed must include a run date, time, or another
occurrence marker in the title or content.
Changed title or sanitized HTML creates a new entry. Once retention removes an
entry, a later publication of the same content to that feed creates a new entry
with a new ID because the earlier deduplication record is gone.

Publishing is atomic with respect to retention and feed reassignment. A
matching entry is returned if publication is resolved first; if that entry
has already been deleted or moved, a new entry is created. A later
operation may still delete or reassign an entry returned by a successful
publication.

The response keeps its existing `result` and `id` fields and does not include
feed metadata. IDs are opaque; clients should store and return them unchanged
when following entry URLs.

The `feed` field accepts a valid identifier or `null`. An empty string or
malformed identifier returns `422`; a non-string, non-null value returns `400`.

### Optional structured data

`data_json` accepts an object, array, string, number, or boolean. For a new entry,
omitting the field or sending `null` means no attachment. JSON never changes
the deduplication key. Empty objects and arrays are attachments. HTML
remains required; JSON is never sanitized as HTML or rendered into the entry page.

Example:

```json
{
  "title": "Morning briefing",
  "content_html": "<p>Three systems reported healthy.</p>",
  "data_json": {
    "healthy_systems": 3,
    "sources": ["https://example.org/status"]
  }
}
```

Send a native JSON value, not a string containing serialized JSON. Feedway does
not require a schema or interpret the document's fields. Its contents are public
through the attachment endpoint, under the same access model as the HTML page.

Feedway first checks the 256 KiB byte limit, then validates UTF-8 encoding and
JSON syntax. It stores the JSON value without decoding or reserializing it;
whitespace inside the value, key order, duplicate keys, number spellings, and
string escapes are preserved. Feedway does not interpret or normalize them.
The syntax check also rejects literal NUL bytes. An escaped `\u0000` is valid
JSON and remains escaped in storage and the attachment response.

### Known deduplication limitation

Within one feed, the final title and sanitized HTML identify an entry. Changing,
adding, or omitting `data_json` while keeping those fields unchanged returns
`deduplicated` and the same ID. The first successful publication wins: its JSON
attachment remains unchanged, including when that first entry had no
attachment. Deduplication never updates stored content or adds or removes an
attachment. This is a deliberate simplification; a producer that needs a new
JSON document must also change the final title or HTML, for example with an
occurrence marker. Publishing that content to a different feed creates a
separate publication.

The field limit applies once to the raw JSON value's bytes, including quotes
and escapes. Data over the limit is rejected, never truncated. The complete
request must still fit within 1 MiB. Malformed JSON returns `400`; data exceeding
the field limit or using invalid UTF-8 returns `422`.

Expected error statuses are:

| Status | Meaning |
| --- | --- |
| `400` | Invalid JSON, more than one JSON value, or `feed` has the wrong JSON type |
| `401` | Missing or invalid Bearer token |
| `413` | Request body exceeds 1 MiB |
| `415` | Content type is not JSON |
| `422` | HTML, `feed`, or JSON data violates validation rules or a field limit |
| `500` | Unexpected publishing failure |

Application errors use one JSON shape:

```json
{"error":"content_html is required"}
```

Successful and error responses from the publishing endpoint use
`Content-Type: application/json; charset=utf-8`.

## Read the feed

### `GET /feed.json`

The aggregate response is [JSON Feed 1.1](https://www.jsonfeed.org/version/1.1/)
with the title `Feedway`. It includes every retained entry, whether assigned to
a feed identifier or unassigned. Entries are newest first, up to
`FEED_RESPONSE_MAX_ENTRIES` (100 by default) and subject to the byte limit.
The top-level object contains `version`, `title`, `_feedway`, and `items`, plus
`home_page_url` and `feed_url` when `BASE_URL` is set. Each
item contains `id`, `url`, `content_html`, `date_published`, and
an optional `title`. When `BASE_URL` is set, `url` is an absolute public
permalink; otherwise it is relative to the origin root, such as `/entries/{id}`.

With `BASE_URL=https://feed.example.com`, the aggregate feed advertises
`home_page_url: "https://feed.example.com/"` and
`feed_url: "https://feed.example.com/feed.json"`. Both fields are omitted when
`BASE_URL` is unset. Feedway uses the configured public origin rather than the
request's host or forwarded headers. URL metadata is included even in empty
feeds and counts toward the 4 MiB limit and the response ETag.

### `GET /feeds/{feed}/feed.json`

Returns the entries assigned to the exact `feed` identifier in a JSON Feed 1.1
whose title is that identifier. The identifier uses the format described in
[Feed identifiers](#feed-identifiers). Filtering happens before applying the
same `FEED_RESPONSE_MAX_ENTRIES` count and 4 MiB response limit used by the
aggregate feed. A valid identifier with no current entries, including one whose
entries have expired, returns `200 OK` with `"items": []`. An invalid path
identifier returns `400 Bad Request` with the common JSON error shape.

The filtered and aggregate routes use the same response headers, ETag,
conditional-request behavior, and truncation signal. The feed title makes the
representations distinct. With `BASE_URL` unset, item and attachment URLs stay
origin-root-relative even though this feed URL is nested under `/feeds/`.

When `BASE_URL` is set, a filtered feed advertises its own absolute `feed_url`,
such as `https://feed.example.com/feeds/daily-briefing/feed.json`.
All feeds share the same `home_page_url`, pointing to the existing home page
at `https://feed.example.com/`. There is no separate HTML page for each feed.

An item with structured data also contains one standard `attachments` entry:

```json
{
  "attachments": [
    {
      "url": "https://feed.example.com/entries/0190abcd-1234-7abc-8def-0123456789ab/data.json",
      "mime_type": "application/json"
    }
  ]
}
```

The attachment URL uses the same `BASE_URL` convention as entry permalinks.
Without it, the URL is origin-root-relative: `/entries/{id}/data.json`. Items without data
omit `attachments`. The feed includes only the link, never the JSON document
itself. Attachment metadata counts toward the 4 MiB feed limit.

Example:

```json
{
  "version": "https://jsonfeed.org/version/1.1",
  "title": "Feedway",
  "home_page_url": "https://feed.example.com/",
  "feed_url": "https://feed.example.com/feed.json",
  "items": [
    {
      "id": "0190abcd-1234-7abc-8def-0123456789ab",
      "url": "https://feed.example.com/entries/0190abcd-1234-7abc-8def-0123456789ab",
      "title": "Morning briefing",
      "content_html": "<p>Three systems reported healthy.</p>",
      "date_published": "2026-07-18T08:00:00Z"
    }
  ],
  "_feedway": {
    "truncated": false
  }
}
```

The uncompressed representation is limited to 4 MiB. If the configured number
of newest entries does not fit, Feedway serves the newest complete entries that
do fit; it never serves a partial item. The response uses:

```http
Content-Type: application/feed+json; charset=utf-8
Cache-Control: public, max-age=60, must-revalidate
ETag: "<sha256-of-response>"
Content-Length: <response bytes>
X-Content-Type-Options: nosniff
```

Feedway does not emit `Last-Modified` or compress responses. A reverse proxy
may add compression.

If the feed cannot be loaded, the endpoint returns `500`. Feedway builds the
feed newest-first and stops before the first complete item that would exceed
the maximum size; that item and all older items are omitted. It never returns a
partial item or a feed-size error during normal feed generation.

### Feed completeness

Every successful feed representation includes the top-level JSON Feed extension
`_feedway` with a boolean `truncated` field:

```json
{"_feedway":{"truncated":true}}
```

`truncated` is `true` when the response omits older entries still present in
PostgreSQL because of `FEED_RESPONSE_MAX_ENTRIES` or the 4 MiB response limit. It is
`false` when all currently stored entries fit, including an empty database and
exactly the configured entry count when those entries fit within the byte limit.
Returning the configured maximum count alone does not establish whether the
feed is truncated. Entries are never split or skipped
to make room for older ones: the feed stops at the first item that does not fit.
The extension itself counts toward the byte limit.

Truncation is a normal `200` response and never blocks publishing. It does not
change retention, expose a next page, or promise that the feed covers a given
time window. Entries already deleted by retention cannot make `truncated` true.
Feedway does not emit a warning item or an error status for omitted history.

The signal is part of the response body and ETag: adding or removing an older,
omitted entry can change the ETag even when the visible `items` are unchanged.
`HEAD` and conditional requests keep the same behavior as other feed requests.
An older Feedway version without `_feedway` does not provide this signal;
absence must not be interpreted as `truncated: false`.

Readers that do not recognize the extension ignore it according to the
[JSON Feed extension rules](https://www.jsonfeed.org/version/1.1/#extensions).
The extension does not add a reader UI warning; consumer behavior is outside
this API contract.

### `HEAD /feed.json` and `HEAD /feeds/{feed}/feed.json`

`HEAD` returns the same status and headers as the corresponding `GET` without
a response body. Send that route's `ETag` value in `If-None-Match` to validate
a cached response:

```bash
etag="$(curl --fail --silent --head http://localhost:8080/feed.json \
  | sed -n 's/^[Ee][Tt][Aa][Gg]:[[:space:]]*\(.*\)\r$/\1/p')"

curl --include \
  --header "If-None-Match: $etag" \
  http://localhost:8080/feed.json
```

An unchanged representation returns `304 Not Modified` with no body.
For both feed routes, `GET` and `HEAD` use weak ETag comparison: either
`"<etag>"` or `W/"<etag>"` matches the current tag. `If-None-Match` also accepts
a comma-separated list of tags, including repeated header lines; any matching
tag returns `304`. A standalone `If-None-Match: *` returns `304` for an existing
feed representation, including an empty feed. Malformed field values are
ignored and the request returns the normal `200` response.

## Read an entry

### `GET /entries/{id}`

Returns one retained entry as a minimal HTML document. The page uses the entry
title for both `<title>` and `<h1>`; an entry without a title uses `Feedway` for
`<title>` and omits `<h1>`. The stored, sanitized `content_html` is rendered
inside `<article>` without additional styling or JavaScript.

JSON Feed items use this endpoint as their `url`. `BASE_URL` makes it absolute;
without that setting, it remains relative to the origin root as `/entries/{id}`.

A successful response uses:

```http
Content-Type: text/html; charset=utf-8
Content-Length: <response bytes>
X-Content-Type-Options: nosniff
```

If the ID does not exist or retention has deleted the entry, the endpoint
returns `404`. A database or rendering failure returns `500` and is logged
without exposing internal details.

### `HEAD /entries/{id}`

`HEAD` returns the same status and headers as `GET` without a response body.

## Read an entry's JSON attachment

### `GET /entries/{id}/data.json`

Returns the retained entry's stored JSON value directly, without a wrapper
or double encoding. This endpoint is public. A successful response uses:

```http
Content-Type: application/json; charset=utf-8
Content-Length: <response bytes>
X-Content-Type-Options: nosniff
```

The endpoint does not render HTML, send `Content-Disposition`, or provide ETag
or conditional requests. The response can be any permitted JSON value, not
necessarily an object. It returns `404` for an unknown entry, an entry without
data, or data removed by retention. A database failure returns `500` and is
logged without exposing internal details.

### `HEAD /entries/{id}/data.json`

`HEAD` returns the same status and headers as `GET` without a response body.

## Health and readiness

### `GET /healthz`

Returns `200 OK` when the process is alive. It does not query PostgreSQL.

### `GET /readyz`

Returns `200 OK` after startup has completed and PostgreSQL responds. It returns
`503 Service Unavailable` while startup is incomplete, PostgreSQL is unavailable,
or shutdown has started.

The `503` response uses the common error shape:

```json
{"error":"not ready"}
```

## Routing and errors

Unknown paths and unsupported methods use the standard Go `net/http` `404` and
`405` responses. They are not wrapped in Feedway's JSON error shape.
